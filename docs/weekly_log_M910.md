# Failure-Driven Engineering Log: Weeks 9 and 10 (candidate entries)
These are problems that really occurred while building and testing Weeks 9 and 10 in my sandbox. Use the ones you hit in your own runs and add your own.

## Week 9
| Question | Response |
|---|---|
| What changed? | A replicated object store, a name server, a transparent client (access, location, replication, migration, failure transparency) and a non-transparent baseline; seven experiments with hypotheses H9.1 to H9.7. |
| What failed? | (1) **Split brain:** a primary that hung, was replaced and resumed acknowledged a write from a client with a stale cache (the write was lost). (2) The outage metric measured gaps between operation START times, so an operation that started early and retried for 3 s hid the outage (the baseline read 0.014 s instead of about 6 s). (3) The availability model predicted rf=1 at 0.73 but 0.82 was measured. (4) The data-loss check missed loss after a restart because new writes pushed the version back above the old maximum. (5) Killing a node is too easy to detect (connection refused at once). (6) H9.6 (the monitor shortens the outage) was NOT SUPPORTED. |
| Why did it fail? | (1) Two queued requests reached the resumed primary: the first was rejected by the backup and fenced it, the second was already waiting on the lock, never re-checked its role, and skipped the backup because a STALE reply had marked it "dead". (2) Start time is not completion time. (3) The model ignored the 1 s retry window of the client. (4) Version level, not version regression, was tested. (5) A crash is not a hang. (6) The client's own timeout already triggers the promotion as fast as a periodic ping can. |
| How was it fixed? | (1) Re-check the role under the lock; do not treat STALE as a dead backup; the zombie replies MOVED. Fenced in 4 of 4 repeated runs afterwards. (2) Outage = longest gap between COMPLETED operations. (3) Model: unavailable time = sum of max(0, outage - retry window). (4) Detect regressions in acknowledged versions. (5) Added a hang (SIGSTOP) fault and a fencing experiment. (6) Reported as a finding. |
| What alternative was considered? | Leases instead of epochs for fencing (needs synchronised clocks); quorum writes instead of primary-backup (higher write cost). |
| What was learned? | A hypothesis test found a real concurrency bug: test the failure you are protecting against, with the timing that makes it likely. A metric must be checked against a case where the right answer is known. A refuted hypothesis is a result. |

## Week 10
| Question | Response |
|---|---|
| What changed? | Six name-resolution schemes (static, broadcast, nameserver, cached nameserver, prefix table/zones, cached prefix), a master with journal and read-only zone servers, and process management (workflows, placement policies, write-ahead durable state, leader as coordinator, recovery). |
| What failed? | (1) Broadcast was counted as 8.6 messages instead of 10. (2) The cached resolvers showed 0% wrong answers after a migration. (3) Registering 2000 names crashed with a line-length error. (4) After a coordinator restart the workflow counter restarted at 1, reissued old IDs, and a surviving manager answered "DONE" for them: the coordinator-failure test reported 12 of 12 completed when the run had really failed. (5) The "processes run twice" metric counted 2 although none completed twice. (6) The resource-release check never succeeded. (7) The CSV writer failed on rows from different sub-tests. (8) H10.5 was NOT SUPPORTED on mixed task sizes. |
| Why did it fail? | (1) The outstanding requests were cancelled after the first answer, but the servers still sent the replies. (2) Warming six resolvers took longer than the 2 s TTL. (3) asyncio's default 64 KB line limit. (4) The ID had no per-boot component and the reset did not clear coordinator memory. (5) A process lost with the killed coordinator (it was also a worker) is restarted, which is not a double execution. (6) Site nodes keep CPU reserved for their sensor and heartbeat services, so free CPU is never 100. (7) Different columns per sub-test. (8) The stale registry sees every node, probe2 only two. |
| How was it fixed? | (1) Let the replies finish and count them. (2) Warm the cached ones last, migrate concurrently, check them first. (3) Stream limit 16 MB. (4) IDs contain a boot nonce; the reset clears coordinator state. (5) Separate "completed twice" from "restarted"; plus write-ahead placement (the chosen node is persisted before the start command). (6) Compare with each worker's idle level. (7) Union of columns. (8) Reported. |
| What alternative was considered? | Persist every state change (more writes) instead of write-ahead placement only; consistent hashing instead of zones. |
| What was learned? | Failure experiments must verify that the failure happened and was not masked by leftover state. Count what the network really carries, not what the client waits for. Name the metric exactly (started twice is not completed twice). |
